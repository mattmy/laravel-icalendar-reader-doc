# 效能與安全

## 效能特性

- 即使從 stream 讀取，完整行事曆仍會留在記憶體中。所需記憶體高於 `.ics` 檔案大小；
  屬性、元件、參與者、提醒與時區定義都會增加負擔。
- 對大型行事曆重複呼叫 `events()`、`todos()`、UID 查詢、`properties()`、
  `components()` 或範圍查詢會增加負擔；可以時請保留並重用查詢結果。
- `toArray()`、`toJson()`，尤其 `toComponentArray()`，會建立完整輸出資料；大型
  Calendar 不要在不需要時同時產生多種格式。
- 大型行事曆呼叫 `rawComponent()` 可能較耗資源，請取得一次後重用。
- `occurrencesBetween()` 會建立完整查詢結果且不快取。單次查詢最多評估所有重複事件
  合計 3,500 個候選；超過時拋出 `RecurrenceLimitExceeded`，不回傳
  部分結果。請使用實際需要的最小範圍。
- `eventsBetween()` 與 Todo 查詢不展開 recurrence，只回傳 `.ics` 中實際存在的 components。

請使用實際最大的行事曆測試，再決定 `max_bytes` 與執行程序的資源上限，並預留
同時處理多個請求及額外記憶體的空間。大型匯入建議使用有記憶體與時間限制的佇列。

## 安全

- 匯入前先驗證上傳檔案，並確認使用者有匯入權限。
- 不可直接把使用者指定的伺服器路徑傳給 `fromPath()`；套件不會下載 URL。
- 用戶端提供的 MIME 與檔名不可信，應以讀取結果或例外判斷內容是否合法。
- 行事曆可能包含個資與惡意文字或 URL；顯示前須跳脫文字，開啟連結前須驗證，
  並避免記錄完整輸入或輸出。保留下來的未知屬性與參數也不可信。
- `max_bytes` 不能取代網頁伺服器的上傳限制、逾時、請求頻率與程序記憶體限制。
